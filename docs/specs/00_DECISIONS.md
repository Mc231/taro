## Purpose

The six specs were written in parallel and disagreed on concrete names and behaviours. This file is the single record of how each disagreement was settled. Every row names the winning resolution and the spec sections that now carry it. Edited sections carry a "Reconciled by 00_DECISIONS.md RCx" note, so a reader can trace a name back to its decision.

Rules:
- **An RC row overrides every spec.** If a spec still contradicts a row here, the spec is wrong. Fix the spec and cite the RC.
- **Spec ownership when there is no RC:** product behaviour and screen states → 01; wire format, config key names, retention and money logic → 03; prices, packs and ad rules → 04; store and legal copy, the safety pass bar → 05; test and coverage rules → 06 (README §1).
- The canonical names themselves (IDs, endpoints, tables, config keys, ports) are listed in `GLOSSARY.md`. This file records *why* a name won; the glossary records *what* the name is.
- RC1–RC48 fix naming conflicts found while the phase plan was written; they were applied on 2026-09-27. RC49–RC93 are review-pass decisions, applied to the specs on 2026-09-26 (Draft v1.0.1) and confirmed in Phase 1. RC94 records the glossary-defined names. RC95 is an owner decision of 2026-09-27 taken after Phase 2 started (package consolidation). RC96 registers the Phase 4 `taro_core` names (2026-09-28). RC97 is an owner decision of 2026-09-29 (LLM-provider-agnostic AI layer). RC99 is an owner decision of 2026-10-05 (wider tablet layouts).
- Every default in this log was confirmed by the owner on 2026-09-27, with no overrides. RC24 records the owner's decision to ship universal apps.

## How to add an RC

1. Take the next free number (currently **RC100**). Never renumber and never reuse a number, even for a withdrawn row.
2. Add one row to the table: topic, the conflict with spec and § references, the resolution, the spec sections edited, and the date (`YYYY-MM-DD`).
3. In the same change, edit every affected spec section and add "Reconciled by 00_DECISIONS.md RCx" next to the edited decision row (PR/AR/BE/MO/CS/QA) or section.
4. If the row changes a canonical name, update `GLOSSARY.md` and grep the specs and the phase docs for the old name. Only this file and the Phase 1 doc may still contain it.
5. If the row changes or replaces an earlier one, do not delete the earlier row. Add "Superseded by RCy" or "Amended by RCy" to its resolution cell (see RC12, RC23, RC43).
6. Docs-only commit: `docs(taro): <summary> (RCx)`.

## Override procedure

A default can be overridden only by the owner.
1. Record the override in the row: keep the old text, add **Override (YYYY-MM-DD, owner):** followed by the new resolution, and update the Date cell.
2. Record the owner's answer under "Owner decisions" below if it has a cost or legal impact.
3. In the same commit, edit the affected specs, `GLOSSARY.md` and every phase doc that assumes the old default (phase docs cite RC numbers, so grep `RCx`). If a phase dependency changes, update `../phases/README.md`.
4.
