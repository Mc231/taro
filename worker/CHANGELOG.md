## [Unreleased]

### Added

- Phase 7.1 ledger and consumption: `BalanceService.hold/refund/commit` (03 §5.3). A hold is one D1 batch holding the free, bonus and paid paths, each gated by a compare-and-set on `readings.hold_state` + `attempt` that carries its balance condition (`free_used < MAX(free_limit, current)`, the Android `device_daily_usage` counter, or `SUM(ledger) >= 1`), with the follow-up writes chained on `(SELECT changes()) = 1` (`src/repos/batchGuard.ts`; spike in `test/integration/db/batchConditional.test.ts`, docs/ARCHITECTURE.md §Ledger). Live holds are renewed, expired ones refunded and replaced by a new attempt; no credit → `no_credit` and a `402 INSUFFICIENT_CREDITS` result with `details.freeResetsAt` and `details.reason` (`noCredits | lowTrustCap | freePaused`). Refunds use the hold's own `hold_local_date` on both usage tables or a `reading_refund` / `reading_undelivered` entry for `{readingId}#{attempt}`; a commit after a cron refund re-holds a new attempt in the same batch or logs `commit_after_refund`. Every applied batch bumps `state_version`. Low-trust free holds count the `lt:ip` prefix cap (CGNAT ASN override) and the alert-only `lt:bucket`.
- `domain/ledgerRules.ts` (cost 1, refund reasons → ledger reason / status, attempts), `domain/consumptionOrder.ts` (free → bonus → paid, free skips, `insufficientReason`, `paidBlocked`, `purchasesAllowed`); `domain/allowance.ts` now uses them.
- fast-check property test `test/unit/domain/ledger.property.test.ts` over random interleavings of hold, refund, commit, grant, revoke, the stale-hold cron, idempotency takeovers and parallel races (bonus ≥ 0, usage bounds and conservation on both usage tables, one hold and one refund per attempt, strictly increasing `state_version`).
- Phase 7.2 purchase verification: `POST /v1/purchases/verify` **[idem]** (03 §6.2, §6.3; RC4) via `PurchaseService.verifyApple` / `verifyGoogle`. iOS: App Store Server API lookup, bundle in `purchases.allowedBundleIds`, `Consumable`, catalog product (active or retired, else `422 PRODUCT_UNKNOWN`), no `revocationDate`, `Production` or `Sandbox` (tagged `environment='sandbox'`, `is_test`). Android: `purchaseState` 0 → grant, 2 → `202 {status: pending}`, 1 → `422`; consumed-and-unknown → `422 consumed`, consumed-and-known → `already_granted`; license-tester purchases are `is_test`; an obfuscated-ID mismatch is logged and counted (`binding_mismatch`), never blocking (RC9). One grant batch (`purchases` insert gate with the RC63 sandbox caps per install and global per UTC day → `422 sandbox_cap`, ledger `purchase`, `state_version`); same install → `already_granted`, another → `409 PURCHASE_ALREADY_CLAIMED`. iOS `appAccountToken` bound to another active install → never granted to the caller: granted to that install, caller gets `409` (RC85). `transferEligible` + `transferToken` (`src/monetization/transferToken.ts`, `TRANSFER_TOKEN_KEY`, 7 days) only when the caller proved the store account (iOS client `signedTransaction`, Android purchase token). Blocked or indebted installs are granted (`blocked_purchase`, RC66); `sandbox_volume` alert at 50 % of the global cap. Google purchases are acknowledged server-side after the grant (RC10); a failure is logged as `pending_ack` and marked `ack:pending:{purchaseId}` in `CACHE_KV` for the retry cron. Store outages → `500 INTERNAL` (retryable).
- Adapters: `AppleAppStoreServerApi` (ES256 JWT from `APPLE_ASC_*`, production then sandbox on `4040010`), `AppleJwsVerifier` (x5c → pinned Apple Root CA G3 `adapters/apple/appleRootG3.ts`, leaf/intermediate OIDs, ES256), `GooglePlayDeveloperApi` (`purchases.products.get`, `:acknowledge`, `voidedpurchases.list`; `androidpublisher` OAuth token cached in `CACHE_KV`), wired by `src/storeDeps.ts`. `PRODUCT_CATALOG` helpers `consumableProduct` and `productIdsFixture`; `test/fixtures/product_ids.json` exported for the Dart `TaroProducts` test.
- Phase 7.3 store webhooks (03 §6.4, RC4): `POST /v1/webhooks/appstore` verifies the ASSN v2 `signedPayload` and the inner `signedTransactionInfo` (x5c → Apple Root CA G3), dedupes on `notificationUUID` in `webhook_events`, and handles `REFUND` → `RefundService.revoke`, `REFUND_REVERSED` → re-grant (`purchase_reversal_regrant`, status `reversal_regranted`), `ONE_TIME_CHARGE` → grant to the install bound by `appAccountToken` through the `verifyApple` checks and grant batch, `CONSUMPTION_REQUEST` → `PUT …/transactions/consumption/{id}` only while `purchases.apple.sendConsumptionInfo` is on (default off, BE Q4), `TEST` → log; other types (incl. `REVOKE`) are `ignored`. `200` once verified, `400` only for a bad signature, `500` when handling failed (the event is `failed` and Apple's retry runs again).
- `POST /v1/webhooks/googleplay`: Pub/Sub push OIDC JWT checked before the body (`GoogleJwksOidcVerifier`: RS256, issuer `accounts.google.com`, `aud == GOOGLE_PUBSUB_AUDIENCE`, `email == GOOGLE_PUBSUB_SA`, `email_verified`; Google JWKS cached 6 h in `CACHE_KV` `google:jwks`, refetched on an unknown `kid` at most once a minute; unset secrets refuse every push), dedupe on `messageId`; `voidedPurchaseNotification` → revoke (by token, then `orderId`; subscriptions ignored), `ONE_TIME_PRODUCT_PURCHASED` → verify, grant to the install bound by `obfuscatedExternalAccountId` and acknowledge, `testNotification` → log. `204`; `401` without a valid token; `500` on a store outage.
- `RefundService.revoke` (03 §6.5, MO16, RC66): one batch gated on the `purchases` CAS: ledger `refund_revoke` (paid may go negative → `paidBlocked`, `purchasesAllowed = false`, `refundDebt`), `refund_count + 1`, `state_version + 1`, and `status = 'blocked'` at `abuse.refundBlockThreshold`. `RefundService.regrant` for reversed refunds. Refund → reversal → refund cycles use `{purchaseId}#n` ledger refs. Metric `purchase_revoked` (source in `code`).
- Crons: `retryPendingAcks` (hourly: re-checks and acknowledges `ack:pending:*` purchases, clears markers of acknowledged, consumed, revoked or unknown ones) and `voidedPurchasesBackstop` (daily: `voidedpurchases.list` for the last two days, paged, revoking anything the RTDN missed).
- Webhook signature failures emit `webhook_sig_failed` (`code` = `apple:payload | apple:transaction | google:oidc`).
- Phase 7.4 rewarded ads via AdMob SSV (03 §7, RC56, RC57): `POST /v1/rewards/intents` **[idem] [attest]** (`rewarded.enabled`, allowed ad unit, cap on install and device key, cooldown from the last grant, `device_reused`, low-trust IP-prefix cap; one batch re-checks cap and cooldown in SQL, bumps `state_version` and cancels the other open intent; `201 {intentId, customData, userId, amount, expiresAt}` with `customData == userId == intentId`; `403 REWARDED_DISABLED`, `409 REWARDED_DAILY_CAP` `reason: cap | cooldown` + `availableAt`), `GET /v1/rewards/intents/{intentId}` (`balance` once granted) and `POST /v1/rewards/intents/{intentId}/cancel` (`204`, idempotent; 2-minute SSV grace kept in `expires_at`).
- `GET /v1/ads/admob/ssv`: ECDSA-SHA256 over the raw query prefix (`AdmobSsvVerifier`), verifier keys from gstatic cached 24 h in `CACHE_KV` and refetched on an unknown `key_id` (`GstaticAdmobKeyProvider`); `transaction_id` dedupe (`webhook_events` `ssv:{id}` and `admob_txn_id`), `user_id == custom_data`, ad unit allow-list, no cap or cooldown re-check; the grant batch books the intent's snapshot amount to `bonus` and counts `rewarded_granted` on `daily_usage` and `device_daily_usage`. `403` only for a bad signature; signed rejections are `200` with `ssv_rejected{reason}`. Metrics `reward_issued`, `reward_granted` (lag in `latencyMs`), `reward_rejected`.
- Cron `expireRewardIntents` (`*/15 * * * *`): `issued` intents past `expires_at` → `expired`, with a `state_version` bump.
- Phase 7.5 support tooling (03 §6.6, 04 §12.9; RC61, RC84; no admin route): `npm run credits-transfer -- --env <env> --ticket <id> --code <transfer code> --support-id <8 hex> [--dry-run] [--local]` over `src/admin/creditsTransfer.ts` verifies the transfer code (`TRANSFER_TOKEN_KEY` from the environment, 7-day TTL) and the Support ID, and moves `min(unspent paid of the old install, purchase credits)` with paired `admin_adjust` entries `{ticket}#out` / `{ticket}#in` (idempotent per ticket, single use per purchase, every statement guarded so a partial run resumes). `npm run ledger-adjust` over `src/admin/ledgerAdjust.ts`: `--bucket/--delta/--note`, `--settle-debt`, `--block`, `--unblock`; install by Support ID (paged scan), `--txn` or `--install`. Both apply via `wrangler d1 execute DB --json --command`, print install prefixes only and confirm by re-reading (`src/admin/d1.ts`).
- `npm run metrics -- --query <events|verify|purchases|rewards|ssv-lag|alerts>` (`scripts/metrics.ts` over `src/admin/metrics.ts`): Analytics Engine SQL API reports (verify outcomes and p95, grants/revocations/sandbox/blocked, rewards by reason, `ssv_grant_lag_ms` p50/p95 from `reward_granted.latencyMs`) and alert rules: verify error rate > 2 % over 10 min, `ssv_rejected` spike, sandbox volume, `blocked_purchase` (exit 3 when one fires).
- Metric `purchase_verify` (every verify outcome in `code`, latency) for the verify error rate; `blocked_purchase` grants now also send a support alert. Alert kinds `verify_error_rate`, `ssv_rejected_spike`, `blocked_purchase`.
- Contract fixtures `purchases.verify.*`, `rewards.intent.*` and `errors.{purchase_already_claimed,purchase_invalid,product_unknown,rewarded_daily_cap,rewarded_disabled}`.
- The 03 §15.2 money-flow integration test `test/integration/flows/moneyFlow.test.ts`: register → `GET /v1/balance` → free hold → `402 INSUFFICIENT_CREDITS` → rewarded intent → signed SSV → bonus hold → `POST /v1/purchases/verify` → paid holds → App Store `REFUND` webhook → `paidBlocked` + `purchasesAllowed = false` (`refundDebt`), all through `buildApp` over real D1/KV (reading holds via `BalanceService` until Phase 8).

- Phase 6.5 contract: `openapi/openapi.json` (OpenAPI 3.1, generated from the zod routes by `npm run openapi`; `npm run openapi:check`, a test and the static CI job fail on drift). Every operation carries `security`, `x-taro-auth` and `x-taro-flags` from one `routeGuards()` helper that also builds its middleware; a wiring test checks them against the GLOSSARY §4 table (RC11).
- Contract fixtures `test/contract/fixtures/{installs,balance,config,timezone,errors}.*.json`, exported by `test/contract/fixtures.test.ts` as file snapshots (`npm run contract:update`) and validated against the route schemas; copied to the app by `melos run contract:sync`.
- `scheduled()` with the three 03 §12 cron triggers (`wrangler.toml` `[env.*.triggers]`, `src/scheduled.ts`); the hourly trigger purges expired `idempotency_keys` and `used_challenges` in bounded `LIMIT 500` batches. The other jobs arrive in Phases 7 and 8.
- `WebhookAlerter` sends each alert kind at most once per hour (last-sent instant in `CACHE_KV` `alert:last:{bucket}`; `Alert.dedupeKey` separates budget tiers); fails open when KV is unavailable.
- Owner CLIs `npm run gen-keys -- --env <env>` (Ed25519 JWKS and the random Worker secrets as JSON on stdout; `--rotate` prepends keyring keys; never `DEBUG_ATTESTATION_TOKEN` for prod) and `npm run smoke -- --env <env>` / `tools/worker_smoke.sh <env>` (health, config, and on staging a debug-attested registration plus a balance read).
- `.gitea/workflows/worker-deploy.yml`: staging on `main`, production canary (10%) on tag `worker-v*`, promotion to 100% by a manual dispatch with an approval input; skips with a warning while `CLOUDFLARE_API_TOKEN` is absent or `wrangler.toml` holds placeholder IDs.

- Phase 6.3 identity and attestation: `POST /v1/attest/challenge` (stateless HMAC challenge, 5-minute TTL, replay detection in `used_challenges` via `UsedChallengeRepo`, `powBits`), `POST /v1/installs` **[idem]** (App Attest / Play Integrity Standard / `type: none` with proof-of-work; `installSecret` ownership proof or an iOS assertion by the stored key for re-registration, 5 per day, `token_generation` bump, `deleted` rows reactivated; per-prefix registration caps; Android `device_key_hash`, iOS DeviceCheck `device_reused`; `purchaseBinding` with UUIDv5 `appleAccountToken` / HMAC `playAccountId`; the response embeds `BalanceDto` and `PublicConfigDto`) and `POST /v1/installs/token` **[attest]** (accepts an expired token).
- Adapters: `AppleAppAttestVerifier` (CBOR via `cbor-x`, x5c chain to the pinned Apple App Attestation Root CA via `@peculiar/x509`, nonce extension, rpIdHash, counter, per-env aaguid, assertions), `GooglePlayIntegrityVerifier` (Standard API `decodeIntegrityToken`, service-account OAuth token cached 50 min in `CACHE_KV`, request hash, package, recognition, device integrity, 120 s age), `AppleDeviceCheckApi` (ES256 JWT, two bits), `Ed25519TokenSigner` (EdDSA install tokens, `TOKEN_SIGNING_KEYS` JWKS `kid` rotation, 7-day TTL).
- Middleware: `auth` (signature, expiry → `TOKEN_EXPIRED`, `status`, `gen == token_generation`) and `attestation` (`aa1.` / `pi1.` / `none`, per-call `clientDataHash`, `attest.requiredOnReadings`, low-trust downgrade on outages). Debug attestation (`X-Taro-Debug-Attestation`) is honoured only when the deploy env sets `ALLOW_DEBUG_ATTESTATION` (RC86).
- Phase 6.1 app skeleton: `Env` with every GLOSSARY §6.1/§13 binding, var and secret; `Deps` with all 03 §1 ports (`src/ports/`) and `makeProdDeps(env)` (prod test-var guard, lazily parsed secrets, WebCrypto/UUID/JSON-logger/Analytics Engine/webhook-alerter adapters; later-phase adapters reject until implemented).
